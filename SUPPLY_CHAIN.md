# Software Supply Chain

DPN Technology maintains machine-readable and human-readable dependency, source-integrity, and production-artifact records for each published DPN AI release.

## Release inventory

The Supply Chain workflow inventories the **immutable release tag**, not the moving main branch.

Each current release receives source and supply-chain records including:

- SBOM.spdx.json — SPDX JSON SBOM generated by Anchore Syft
- SBOM.cyclonedx.json — CycloneDX JSON SBOM generated by Anchore Syft
- SBOM_SHA256SUMS.txt — SHA-256 hashes for both SBOM documents
- SBOM_MANIFEST.txt — repository, release tag, source commit, scanner version, and generation time
- SOURCE_SHA256SUMS.txt — SHA-256 hashes for tracked release-source files
- DEPENDENCY_INVENTORY.txt — readable declared-dependency inventory
- RELEASE_PROVENANCE.json — release/source provenance evidence
- RELEASE_SHA256SUMS.txt — integrity manifest for generated release records

The Release workflow also publishes the production Windows trust bundle:

- DPN-AI-Setup-<version>.exe — Authenticode-signed production installer
- installer-manifest.json — installer hash, signer identity, version, and production-signing state
- source-build-manifest.json — packaged executable hash and signer identity
- update-manifest.json — Ed25519-signed update metadata
- WINDOWS_SHA256SUMS.txt — transfer-integrity hashes covering the Windows production bundle

GitHub dependency-snapshot submission is intentionally disabled until the repository dependency graph is enabled. Release SBOMs remain the authoritative machine-readable inventory.

## Security preflight

Production signing does not begin until the Release workflow:

1. validates the requested version and tag
2. runs the repository guard
3. runs the DPN source security scanner
4. installs the pinned audit toolchain from .github/requirements-security.txt
5. runs pip-audit across:
   - requirements.txt
   - requirements-build.txt
   - requirements-browser.txt
   - requirements-desktop.txt
   - requirements-voice.txt

This prevents a manual release dispatch from bypassing dependency or security gates.

## Scanner reproducibility

Security and SBOM tooling is pinned to reviewed versions or immutable GitHub Action commit SHAs. This prevents an unreviewed tool update from silently changing release evidence.

The declared application dependencies are bounded but are not yet a complete transitive Python lock using require-hashes. Exact resolved dependency locking remains a separate reproducibility improvement; release SBOMs, dependency inventory, and vulnerability audits provide current resolution evidence.

## Windows production trust

Windows release artifacts use two independent trust mechanisms:

1. **Authenticode** for the executable and installer, using a production code-signing certificate imported ephemerally on the Windows runner.
2. **Ed25519** for update metadata, using a private signing seed stored only in GitHub Secrets and a separately configured matching public key.

The release builder requires HTTPS timestamping, validates signer thumbprints, self-verifies the generated Ed25519 signature, re-hashes the installer, and clears temporary signing material before exit.

The Windows build job also creates GitHub/Sigstore SLSA build-provenance attestations for the signed production bundle. The Ubuntu publication job independently re-verifies the transferred bundle, creates a separate provenance attestation for the source archive it builds, and only then creates the GitHub Release.

## Verification

Verify release SBOMs with sha256sum against SBOM_SHA256SUMS.txt.

Verify tracked source files from a checkout of the tagged release with sha256sum against SOURCE_SHA256SUMS.txt.

Verify the Windows bundle with sha256sum against WINDOWS_SHA256SUMS.txt.

Authenticode and Ed25519 verification are additionally enforced inside the production release workflow. GitHub artifact attestations provide an additional Sigstore-backed provenance record for workflow-built release artifacts.

## Release traceability

The intended chain is:

Source + VERSION
→ CI / Tests / CodeQL / Security Gates
→ Release Security Preflight
→ Ephemeral Production Signing
→ Authenticode-Signed Windows Installer
→ Ed25519-Signed Update Manifest
→ Windows SHA-256 Bundle
→ GitHub/Sigstore Windows Build Provenance
→ Independent Ubuntu Bundle Verification
→ GitHub/Sigstore Source Archive Provenance
→ GitHub Release + Immutable Tag
→ Exact Tag Supply-Chain Inventory
→ SPDX + CycloneDX SBOMs
→ Source Hashes + Dependency Inventory + Provenance

## Inventory scope

The DPN dependency inventory searches declared dependencies from common repository manifests including Python requirements, Node package manifests, Gradle or Maven coordinates, Docker base images, and GitHub Actions references.

Runtime plugins, operating-system packages, externally installed AI models, infrastructure dependencies, and services not declared in the repository can require a separate operational inventory.

## Security

SBOM, release, and inventory files must never contain production passwords, tokens, API keys, private keys, PFX contents, live databases, backups, employee or customer data, or private operational exports.
